# 코드 검수 요청 — 평가문항 자동 출제 툴 (프로토타입)

## 1. 검수 방식
- **이번 검수는 읽기 전용이다.** 코드를 고치지 말고 발견 사항만 보고한다(수정은 결과를 보고 따로 진행한다).
- 테스트와 모의(mock) 실행은 해도 된다. **실제 LLM 호출(anthropic / openai_compat / claude_agent_sdk 공급자)은 하지 않는다.** 비용이 발생한다.
- 보고 형식은 7절을 따른다.

## 2. 이 툴이 하는 일
성인 온라인 강의 원고(PDF·PPTX·DOCX·HWP)를 넣으면 원고당 약 300문항(선다형 4지·진위형 OX·단답형)을 출제한다. 산출물은 두 가지다.
- 지정 양식의 엑셀
- 원고 위에 출처를 하이라이트한 근거PDF

다른 팀의 서비스에 그대로 쓰이므로 **문항 오류가 곧 사고**다.

파이프라인: 원고 등록 → 출제자 대시보드(옵션) → 출제(자동 검증 G1~G6) → 사람 검수(G7) → 출력

### 최우선 요구사항 — 검수의 기준
| # | 요구 | 구현이 보장해야 하는 것 |
|---|---|---|
| ★1 | 원고 전 범위에 고르게 출제(지엽 출제 금지, 필요하면 페이지별 강제 할당) | 생성 전에 코드가 페이지별 슬롯을 배분하고, 출제 후 0문항·과밀 페이지를 경고한다 |
| ★2 | 출처를 원고 위에 표시(기존 `2026_E-TEST_30문항_근거PDF_추출본.pdf`와 같은 방식) | 출처 쪽수는 LLM이 아니라 코드가 원고에서 찾아 확정한다. 근거를 찾지 못한 문항은 승인·출력할 수 없다 |
| ★3 | 출제 신뢰도 | 관문 G1~G6을 통과하고 사람 승인(G7)까지 받은 문항만 최종 엑셀·근거PDF에 들어간다 |

### 그 밖의 요구
- 난이도는 4단계(최상·상·중·하)이고 대시보드에서 %로 조정한다.
- 추가 출제 시 기존 문항과 중복되면 안 된다. 추가 출제는 난이도별 수량 또는 총 수량 + 난이도 %로 지정한다.
- 출력은 `엑셀_출력 형식(양식).xlsx` 양식을 따른다.

## 3. 규칙의 근거 문서 (프로젝트 루트)
| 문서 | 내용 |

## 4. 실행 방법
```
pip install -r requirements.txt
python -m pytest tests -q                      # 현재 21 passed
streamlit run app.py                           # 대시보드 (사이드바 LLM 설정 = '데모(mock)')
python -m exam_gen.cli new "테스트" input_17-43.pdf
python -m exam_gen.cli run 테스트 --total 30 --provider mock
python -m exam_gen.cli export 테스트 --draft
python -m exam_gen.cli report 테스트
```
- 환경변수 `EXAM_GEN_PROJECTS`로 프로젝트 저장 폴더를 바꿀 수 있다. 테스트 실행에는 임시 폴더를 쓰는 것을 권장한다.
- 실행 환경은 Windows, Python 3.12다. PPTX·DOCX 변환은 Office COM을 쓴다.

## 6. 검수 항목 (우선순위 순)

### A. 신뢰도 관문을 우회하는 경로가 있는가 (가장 중요)
- 근거를 원고에서 찾지 못했거나 G1~G6에서 탈락한 문항이 최종 출력에 들어갈 수 있는 경로가 있는지 본다.
  - 대상: `output/numbering.select`, `excel.write`, `evidence_pdf.build`, `review_ops.approve` / `bulk_approve` / `set_status("restore")`
- 사람이 문항을 수정한 뒤 G4·G5 재검증 없이 승인되는 흐름이 의도대로 경고되는지 본다(`review_ops.save_edit`, `llm_stale`).
- G4 독립 풀이에 정답이나 참·거짓 정보가 새어 들어가지 않는지 본다(`solver.present`의 `with_key=False` 경로).
- G1(`schema.check_structure`)에서 정답 논리를 검사하는 방식이 맞는지 본다.
  - 옳은 것/옳지 않은 것 고르기에서 참 보기 개수
  - 조합형의 참 진술 개수
  - 정답 위치

### B. 근거 매칭(★2)의 정확성 — `validate/evidence.py`
- L1 부분 일치(`_greedy_cover`, 8자 조각, 80% 기준, `_largest_cluster`)가 **의역되었거나 원고에 없는 문장을 근거로 잘못 인정할 수 있는지** 확인한다. 반례를 만들어 보면 좋다.
- 같은 문장이 여러 페이지에 있을 때 `locate`가 고르는 페이지가 적절한지 본다.
- 힌트 페이지 ±1 밖은 L2(정확 일치)만 허용하는 정책이 타당한지 본다.
- 표 셀(블록 순서)과 2단 편집에서 줄 순서 때문에 매칭이 실패하거나 엉뚱한 줄을 하이라이트할 수 있는지 본다.
- 수치 환각 검사(`check_item`의 `numbers_in`)를 피해 가는 경우가 있는지 본다. 예: "20년"과 "이십 년", 소수점·쉼표 표기 차이.
- 단답형 정답어 검사가 띄어쓰기·표기 차이에서 오탐하거나 미탐하는지 본다.

### C. 원고 전반 출제(★1) — `plan/coverage.py`, `plan/slots.py`
- 최대잔여법 배분, 페이지 상한, 추가 출제 가중치에서 합계가 맞지 않는 경우나 극단 입력(페이지 수 > 문항 수, 제외 페이지 다수, 1페이지 원고)에서 깨지는지 본다.
- `slots._fix_margins`가 유형×난이도 주변 합계를 항상 맞추는지 본다. 반올림 오차가 남는 입력이 있는지 확인한다.
- 옳은 것 20% / 옳지 않은 것 80%와 조합형 비율이 함께 지정될 때 계산이 맞는지 본다.

### D. 동시성·상태 관리 — `generate/generator.py`, `store.py`
- `ThreadPoolExecutor`로 페이지를 병렬 처리할 때 다음이 안전한지 본다.
  - 공유 상태(`self.existing`, `self.prog`)
  - SQLite 쓰기(`_LOCK`, 호출마다 새 연결)
  - `next_key` / `save_item`의 키 발급
- 중지·재개(`resume_batch`)에서 같은 슬롯이 중복 저장되거나 빠지는 경우가 있는지 본다.
- 자동 중단(`_autostop_check`) 이후 진행 중이던 페이지가 어떻게 끝나는지 본다.

### E. 출력물 양식 일치
- **엑셀**(`output/excel.py`)
  - 양식의 병합 머리글, 열 순서·서식이 유지되는지 본다.
  - 진위형 정답 1=O·2=X, 보기3·4 공란 규칙을 지키는지 본다.
  - 단답형은 보기 전부 공란에 정답 열에만 값이 들어가는지 본다.
  - 숨김 열(R~Y), 숨김 시트 '검수용(수정표시)'의 색상 규칙을 확인한다(삭제 = 회색, 수정 = 노란 셀에 빨간 글씨).
  - `delete_rows`로 지운 예시 행 때문에 양식에 남는 잔여물(데이터 유효성 검사, 조건부 서식, 행 높이)이 없는지 본다.
- **근거PDF**(`output/evidence_pdf.py`)
  - 기준 추출본과 구성이 같은지 본다(표지 → 인덱스 → 사용 안내 → 문항별 분리자 + 원본 페이지).
  - 라벨 규칙: `Q12-3`, ㄱ→A, `OX`, 단답 `A`
  - 라벨이 겹치거나 왼쪽 여백 밖으로 나가지 않는지 본다.
  - `subset_fonts()`가 원고 PDF 자체의 폰트를 손상시키지 않는지 본다.
  - 300문항 규모에서 파일 크기와 처리 시간이 감당할 수준인지 본다.
- 엑셀 문항번호와 근거PDF 라벨이 항상 대응하는지 본다(`numbering.number`, per_type 모드 포함).

### F. 지침·유의사항 반영 여부
- `llm/prompts/generate_system.j2`, `review_system.j2`, `solve_system.j2`가 근거 문서의 규칙을 빠뜨리거나 잘못 옮겼는지 본다. 근거 문서와 대조해 누락 목록을 만들어 주면 좋다.
- `validate/rules.py`의 정규식에서 오탐·미탐 사례를 찾는다.
  - 문어체 판정(`_POLITE`): 인용문 안의 "~합니다"를 오탐하는지
  - 절대어 판정
  - 단답형 조사 힌트 판정(`_BLANK` 다음 글자)
  - 부정 발문 판정(`_NEG`)
- G5 난이도 판정(두 단계 이상 차이면 탈락) 기준이 합리적인지 본다.

### G. 이미 의심하고 있는 지점 — 사실 여부를 확인하고 영향도를 평가해 달라
1. `generate/generator.py:229` — 조합형 보기 시드로 `hash(s["sid"])`를 쓴다. 파이썬 문자열 해시는 실행마다 바뀌므로 재현성이 깨지는 것으로 보인다.
2. `pages/3_출제진행.py:58` — '이어서 출제' 버튼이 상태가 stopped·error일 때만 보인다. 서버가 재시작되어 상태가 `running`으로 남은 배치는 재개할 방법이 없는 것으로 보인다.
3. `review_ops.revalidate_code` — 승인할 때 G6 중복 검사를 이후 배치 문항까지 포함해 다시 하므로, 정상 문항이 서로를 이유로 승인이 막힐 수 있는지 확인이 필요하다.
4. `store.py` — 원고가 여러 개이면 책 쪽수 라벨이 겹칠 수 있다(예: 두 교재 모두 17쪽). 이때 `evidence.resolve_hint`나 엑셀 'PPT' 열 표기에 혼동이 생기는지 본다.
5. `page_map.py` — 감지된 예외 쪽수(`exceptions`)를 실제로는 쓰지 않는다. 쪽수가 중간에 끊기는 원고에서 문제가 되는지 본다.
6. `llm/settings.py` — API 키가 `data/settings.json`에 평문으로 저장된다.
7. 하이라이트는 줄 단위라 인용문 앞뒤의 다른 문장까지 칠해진다. 기존 추출본도 줄 단위이지만, 문자 단위로 줄일 필요가 있는지 의견을 달라.

### H. 테스트 공백
- `tests/test_core.py`가 다루지 못하는 핵심 경로를 짚고, 추가할 테스트 케이스를 제안해 달라. 특히 A·B·D 항목이 대상이다.
